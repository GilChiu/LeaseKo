# Implementation Plan: Clerk Authentication — Next.js Frontend

**Branch**: `007-clerk-auth-nextjs` | **Date**: 2026-05-02 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/007-clerk-auth-nextjs/spec.md`

## Summary

Integrate `@clerk/nextjs` v5 into the existing Next.js 14 App Router frontend. The implementation creates Clerk-hosted sign-in/sign-up pages, wraps the app with `ClerkProvider` in the root layout, adds `clerkMiddleware()` to protect `/dashboard` and all sub-routes, replaces the `UserButton` placeholder in the dashboard header, and updates the home page with `SignedIn`/`SignedOut` conditional navigation. The existing `apiFetch` utility already supports Bearer token injection — no changes needed there.

| T005 | `apps/web/src/middleware.ts` | Create | `clerkMiddleware()` + `createRouteMatcher` for public routes |

**Middleware content**:

```ts
import { clerkMiddleware, createRouteMatcher } from '@clerk/nextjs/server';

const isPublicRoute = createRouteMatcher(['/', '/sign-in(.*)', '/sign-up(.*)']);

export default clerkMiddleware(async (auth, request) => {
  if (!isPublicRoute(request)) {
    await auth.protect();
  }
});

export const config = {
  matcher: [
    '/((?!_next|[^?]*\\.(?:html?|css|js(?!on)|jpe?g|webp|png|gif|svg|ttf|woff2?|ico|csv|docx?|xlsx?|zip|webmanifest)).*)',
    '/(api|trpc)(.*)',
  ],
};
```

`auth.protect()` redirects unauthenticated users to the Clerk sign-in URL automatically.

## Route Protection Rules

| Route | Middleware Behaviour | Notes |
|-------|---------------------|-------|
| `/` | Public | Home page — no auth required |
| `/sign-in(.*)` | Public | Clerk sign-in + sub-routes |
| `/sign-up(.*)` | Public | Clerk sign-up + sub-routes |
| `/dashboard` | Protected | `auth.protect()` → redirect to sign-in |
| `/dashboard/*` | Protected | All sub-routes covered by middleware matcher |
| `/_next/*`, `/*.ico`, etc. | Excluded | Static assets excluded from middleware |

---

## Security Rules

1. **No JWT validation in frontend** — `auth.protect()` redirects, does not verify JWTs
2. **No localStorage** — Clerk manages sessions via cookies/memory; never call `localStorage.setItem('token', ...)`
3. **No hardcoded keys** — `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` from environment only
4. **`CLERK_SECRET_KEY` server-side only** — never reference it in `"use client"` components
5. **Frontend protection is UX only** — NestJS backend (Feature 008) must independently verify every JWT
6. **No authorization logic in frontend** — roles, permissions, and tenant isolation belong in the backend

## Notes for Next Features

### Feature 008 — NestJS JWT Verification (Backend Auth Guard)

- `CLERK_JWKS_URL` = `https://clerk.com/<clerk-instance>/.well-known/jwks.json`
- `CLERK_SECRET_KEY` is already in `apps/api/.env.example` as a placeholder
- The NestJS `AuthGuard` will call `auth().userId` / verify the Bearer token from the frontend
- `userId` extracted from the verified JWT is the canonical user identifier

### Feature 009 — Clerk Organizations / Tenant Mapping

- Enable Organizations in the Clerk dashboard
- `auth().orgId` maps to `tenantId` in the backend
- `OrganizationSwitcher` from `@clerk/nextjs` replaces the org-switcher placeholder in the dashboard header
- Backend must enforce `tenant_id` filters on all queries — never trust `orgId` from the frontend request body
