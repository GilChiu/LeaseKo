# Implementation Plan: Create Renter Contact API

**Branch**: `sprint/003` | **Date**: 2026-06-05 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/040-create-contact-api/spec.md`

## Summary

Implement a `POST /api/v1/contacts` endpoint that allows authenticated landlords to create renter contact records scoped to their workspace. The contact is created in a new `contacts` NestJS module following the four-layer Clean Architecture pattern established by the `properties` and `units` modules. Email uniqueness is enforced per workspace (case-insensitive) at the application layer to support future soft-delete semantics; `tenantId` is always sourced from the verified Clerk JWT context.

## Technical Context

**Language/Version**: TypeScript 5.x / Node.js 20.x
**Primary Dependencies**: NestJS 10, Prisma 5, class-validator, class-transformer, @nestjs/swagger
**Storage**: PostgreSQL (via PrismaService — globally provided)
**Testing**: Jest (unit, integration, E2E)
**Target Platform**: Linux server (Docker / Railway)
**Project Type**: Web service API (NestJS monolith)
**Performance Goals**: < 2 seconds end-to-end per SC-001
**Constraints**: Email uniqueness per tenant (case-insensitive); soft-delete-aware uniqueness check; no BullMQ (create is synchronous and fast); all inputs validated in a single pass via NestJS global `ValidationPipe`
**Scale/Scope**: Single tenant-scoped POST endpoint; one new Prisma model; one new NestJS module

## Constitution Check

_GATE: Must pass before Phase 0 research. Re-check after Phase 1 design._

**Architecture**

- [x] Module follows four-layer Clean Architecture: `domain / application / infrastructure / presentation`
- [x] Domain layer imports no NestJS or Prisma packages — `TenantContact` is a plain TypeScript interface
- [x] Controllers are thin — `ContactsController` delegates directly to `CreateTenantContactUseCase`
- [x] Cross-module interaction uses explicit interfaces or events only — no direct internal imports from other modules

**Multi-Tenancy (CRITICAL)**

- [x] New `tenant_contacts` table includes `tenant_id` column with index (`@@index([tenantId])`)
- [x] All repository queries filter by `tenantId` — no unscoped queries
- [x] `tenantId` injected via `@CurrentTenant()` decorator sourced from `IRequestContext` set by `ClerkJwtGuard` — never from body, query, or header

**Authentication & Authorization**

- [x] Clerk JWT verified by existing `ClerkJwtGuard` via JWKS — no change to auth flow
- [x] `@RequiresTenant()` applied to `POST /contacts` — returns 403 if no active workspace

**Data Layer**

- [x] All DB access through `TenantContactRepository` interface — `PrismaService` only in `PrismaTenantContactRepository`
- [x] Prisma schema `TenantContact` model includes `@@index([tenantId])` and `@@index([tenantId, email])`

**API & Async**

- [x] Endpoint documented with `@ApiTags`, `@ApiOperation`, `@ApiResponse`, `@ApiBearerAuth` Swagger decorators
- [x] `CreateTenantContactDto` uses `class-validator` decorators (`@IsString`, `@IsNotEmpty`, `@IsEmail`, `@MaxLength`, `@IsOptional`)
- [x] No BullMQ — contact creation is synchronous; no heavy/non-critical work to offload
- [x] No BullMQ jobs required

**Testing**

- [x] Unit tests: `CreateTenantContactUseCase` with mocked repository
- [x] Integration tests: `PrismaTenantContactRepository` against real DB
- [x] E2E tests: `POST /contacts` with auth + tenant context

**Security**

- [x] No secrets in source code
- [x] Rate limiting: existing `ThrottlerGuard` covers the new route (globally applied)
- [x] All inputs validated by `class-validator` via global `ValidationPipe` before the use case is reached
