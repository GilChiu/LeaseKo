# Implementation Plan: Clean Architecture Module Structure

**Branch**: `016-clean-arch-module-structure` | **Date**: 2026-05-05 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/016-clean-arch-module-structure/spec.md`

## Summary

Standardize the NestJS backend (`apps/api/src`) into a strict four-layer Clean Architecture module structure (`domain / application / infrastructure / presentation`) for every business module. The majority of the architecture is already in place from features 012–015. This feature fills the remaining gaps: moving two controllers from module roots into their `presentation/` layers, creating empty `domain/` layer directories where absent, adding `application/` and `infrastructure/` scaffold directories in utility modules, and writing the canonical `docs/backend-architecture.md` reference document. No new business features are added and no working logic is rewritten.

### Layer Responsibility Table

| Layer | Allowed Contents | Forbidden Imports |
|---|---|---|
| `domain/` | Entities, value objects, domain errors, domain constants, domain rules | NestJS decorators, `@prisma/client`, `PrismaService`, HTTP request/response objects, external SDKs |
| `application/` | Use cases, repository interfaces, service interfaces, command/query objects, DI tokens | `PrismaService`, `@prisma/client`, controller decorators (`@Get`, `@Post`, etc.), `Request`/`Response` HTTP types |
| `infrastructure/` | Prisma repository implementations, Clerk adapter, Redis/BullMQ adapters, external API clients | Controller decorators, DTO decorators for HTTP responses |
| `presentation/` | Controllers, DTOs, Swagger decorators, route-level validation | `PrismaService`, direct repository implementations, business logic |

### Dependency Direction Rules

```
presentation  →  application  →  domain
infrastructure               →  application / domain
```

**Allowed cross-layer imports:**
- `presentation` → `application` (use cases, interfaces)
- `presentation` → `domain` (domain types for DTO mapping if needed)
- `application` → `domain` (entities, value objects)
- `infrastructure` → `application` (implements interfaces, imports repository interface)
- `infrastructure` → `domain` (entities for persistence mapping)

**Forbidden cross-layer imports:**
- `domain` → any other layer
- `application` → `infrastructure` implementation classes
- `presentation` → `infrastructure` implementation classes directly
- `presentation` → `PrismaService`

### Module Boundary Rules

| Rule | Detail |
|---|---|
| A module owns its business logic | Use cases, domain entities, and application interfaces must not be imported directly by other modules |
| Cross-module via exports only | Other modules may only use what a module explicitly exports from its `*.module.ts` |
| No infra coupling across modules | `modules/auth/` must not import `PrismaUserRepository` from `modules/users/` |
| No circular dependencies | `AuthModule` may export `VerifyClerkTokenUseCase`; other modules import `AuthModule` — not the reverse |

### Prisma Usage Rules

| Location | Allowed? |
|---|---|
| `database/prisma/prisma.service.ts` | ✅ Definition only |
| `modules/*/infrastructure/repositories/prisma-*.ts` | ✅ Only location allowed to inject `PrismaService` |
| `modules/*/application/` | ❌ FORBIDDEN |
| `modules/*/domain/` | ❌ FORBIDDEN |
| `modules/*/presentation/` | ❌ FORBIDDEN |
| `common/` | ❌ FORBIDDEN |
| `shared/` | ❌ FORBIDDEN |
