## Implementation Phases

### Phase 1: Update Swagger Bootstrap Metadata

**Goal**: Align the Swagger metadata in `main.ts` with the spec requirements. This
is a safe, non-breaking change — metadata only affects the documentation UI title
and version badge.

#### Task 1.1 — Update `apps/api/src/main.ts` Swagger config

Change:
```typescript
const config = new DocumentBuilder()
  .setTitle("LeaseKo API")
  .setDescription("LeaseKo Property Management SaaS API")
  .setVersion("1.0")
  .addBearerAuth()
  .build();
```

To:
```typescript
const config = new DocumentBuilder()
  .setTitle("Property Management SaaS API")
  .setDescription(
    "API documentation for the multi-tenant Property Management SaaS backend.",
  )
  .setVersion("1.0.0")
  .addBearerAuth()
  .build();
```

> All other configuration (`ignoreGlobalPrefix: true`, the `SwaggerModule.setup("api/docs", ...)` call, the production guard) is unchanged.

---

### Phase 2: Add Missing ErrorResponseDto Type References

**Goal**: Ensure all error response decorators reference the shared `ErrorResponseDto`
type so the Swagger UI renders the full standard error schema instead of a blank entry.
Satisfies FR-008 (no duplicated inline schemas) and US2 acceptance scenarios.

#### Task 2.1 — Update `auth.controller.ts`

Add `import { ErrorResponseDto }` and add `type: ErrorResponseDto` to the existing
`@ApiUnauthorizedResponse` decorator.

Before:
```typescript
@ApiUnauthorizedResponse({ description: "Missing or invalid Bearer token." })
```

After:
```typescript
@ApiUnauthorizedResponse({
  type: ErrorResponseDto,
  description: "Missing or invalid Bearer token.",
})
```

#### Task 2.2 — Update `tenant-context.controller.ts`

Add `import { ErrorResponseDto }` and add `type: ErrorResponseDto` to both the
`@ApiUnauthorizedResponse` and `@ApiForbiddenResponse` decorators.

Before:
```typescript
@ApiUnauthorizedResponse({ description: "Missing or invalid Bearer token." })
@ApiForbiddenResponse({
  description: "Authenticated but no active organization context.",
})
```

After:
```typescript
@ApiUnauthorizedResponse({
  type: ErrorResponseDto,
  description: "Missing or invalid Bearer token.",
})
@ApiForbiddenResponse({
  type: ErrorResponseDto,
  description: "Authenticated but no active organization context.",
})
```

### Phase 3: Developer Reference Documentation

**Goal**: Create `docs/api-documentation.md` — a concise reference that backend
developers follow when documenting new endpoints. Satisfies US3 and FR-011.

#### Task 3.1 — Create `docs/api-documentation.md`

Content sections:

1. **Swagger UI Access** — URL, how to open it locally, production behavior
2. **OpenAPI JSON** — `/api/docs-json` URL
3. **Bearer JWT Authorization** — step-by-step UI guide
4. **Current Endpoints** — table of all current endpoints with auth status
5. **Endpoint Documentation Pattern** — three copy-paste patterns:
   - Public endpoint (no auth)
   - User-protected endpoint (Bearer required)
   - Tenant-protected endpoint (Bearer + org required)
6. **Response DTO Pattern** — how to create a new DTO with `@ApiProperty`
7. **Error Response Pattern** — always use `type: ErrorResponseDto` with `@ApiUnauthorizedResponse`/`@ApiForbiddenResponse`
8. **Clean Architecture Rule** — where decorators may and may not appear

## Notes for Subsequent Features

### Feature — Health Check Endpoint Refinement (US 6.2)

`GET /health` currently returns a static `{ status: "ok", service: "api", timestamp }`.
A future feature can expand this to check database and Redis connectivity, returning
a richer health status. The Swagger documentation pattern is already in place —
only the controller logic and `HealthResponseDto` would need updating.

### Feature — Future Module Endpoint Documentation

All new controllers in future modules (Properties, Leases, Payments) MUST:
1. Add `@ApiTags("module-name")` on the controller class
2. Add `@ApiBearerAuth()` and `@ApiUnauthorizedResponse({ type: ErrorResponseDto, ... })` on protected controllers
3. Add `@ApiForbiddenResponse({ type: ErrorResponseDto, ... })` on tenant-protected controllers
4. Add `@ApiOperation()` and `@ApiOkResponse({ type: ResponseDto })` on each endpoint method
5. Keep all response DTOs in `modules/*/presentation/dto/`

Reference: `docs/api-documentation.md` (created in this feature).

### Feature — Swagger Error Response Completeness

Currently `400 Bad Request` validation responses are handled by the filter but
no controller uses `@ApiBadRequestResponse`. As new mutation endpoints are added
(POST, PATCH), each should add `@ApiBadRequestResponse({ type: ErrorResponseDto })`.
The `ErrorResponseDto` already supports the `details.fields` shape for validation
errors.

### Feature — Testing Foundation

No new test infrastructure is introduced here. The existing 4-suite Jest configuration
covers unit tests for the filter, utilities, use cases, and health controller. Future
integration tests for Swagger (e.g., verifying the OpenAPI spec programmatically)
would fit as a separate E2E concern.
